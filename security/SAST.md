# Phase 6: static application security testing with Semgrep

## Purpose and scope

SAST asks whether source code uses insecure patterns. Semgrep parses source code
and matches rules against its structure; taint rules can also follow data from a
source to a dangerous operation. It does not need a running Flask server, a
populated database, or application dependencies to parse this project's Python.
It does not execute the application or prove a finding can be exploited.

Semgrep Community Edition 1.182.0 is pinned in `security/requirements-sast.txt`.
The workflow runs it without a Semgrep account or token and disables metrics.
The scanner dependency is separate from the application's requirements and image.

## Selected security rules

The project uses a small, version-controlled ruleset instead of downloading a
changing registry ruleset on each scan. These are project-authored rules, not a
complete Python or Flask security audit.

| Check ID | Rule severity | What it checks |
| --- | --- | --- |
| `python-sql-query-concatenation` | `ERROR` | A concatenation result flows into the query argument of `.execute()` |
| `python-eval` | `ERROR` | Use of Python `eval()` |
| `flask-debug-enabled` | `WARNING` | A `.run()` call explicitly sets `debug=True` |

The SQL rule detects the training application's concatenated user lookup. The
parameterized login query should not match. The debug rule only detects literal
`True`; the environment-driven `DEBUG` variable in this app is not a guaranteed
match. Other existing weaknesses, including plaintext password storage and
verbose errors, are outside this initial ruleset.

False positives are findings that match a rule but are safe in their actual
context. For example, this SQL rule can flag concatenations of trusted constants,
and `.execute()` or `.run()` can belong to APIs other than SQLite or Flask.
Review findings rather than treating every match as a proven exploit. Conversely,
no findings does not prove the application is secure. No blanket exclusions or
inline suppressions were introduced.

## Run locally

From the repository root, in PowerShell:

```powershell
python -m venv .venv-sast
.\.venv-sast\Scripts\python.exe -m pip install -r security/requirements-sast.txt
.\.venv-sast\Scripts\python.exe security/scripts/validate_semgrep.py --semgrep .\.venv-sast\Scripts\semgrep.exe
New-Item -ItemType Directory -Force reports | Out-Null
.\.venv-sast\Scripts\semgrep.exe scan --config security/semgrep.yml --strict --metrics=off --disable-version-check --no-rewrite-rule-ids --json --output reports/semgrep.json app
```

The validation script resolves the executable before changing its working
directory. An absolute executable path with `--semgrep` also works:

```powershell
$scannerPath = (Resolve-Path .\.venv-sast\Scripts\semgrep.exe).Path
.\.venv-sast\Scripts\python.exe security/scripts/validate_semgrep.py --semgrep $scannerPath
```

On Linux/macOS, install the same requirements in a virtual environment, then run:

```sh
python security/scripts/validate_semgrep.py
mkdir -p reports
semgrep scan --config security/semgrep.yml --strict \
  --metrics=off --disable-version-check --no-rewrite-rule-ids \
  --json --output reports/semgrep.json app
```

## Controlled detection and remediation

The validation script creates `example.py` in a temporary directory. It initially
contains a query constructed from `user_id` with string concatenation. Semgrep
scans it using the same ruleset as CI, with `--error` so findings return exit 1.
The script verifies the rule ID, filename, line 6, severity, description, and that
the example was actually scanned without analysis errors.

It then replaces the example with a fixed query and bound parameter:

```python
db.execute("SELECT username FROM users WHERE id = ?", (user_id,))
```

The second scan must return exit 0 and an empty `results` list. The script fails
if either expectation is unmet and removes the temporary files automatically.
The sample code is never executed and no insecure fixture is committed to the
application. This validates the SQL rule; it does not test every rule or possible
Python program.

Expected output includes:

```text
PASS: python-sql-query-concatenation detected at example.py:6; severity=ERROR; exit=1
PASS: parameterized query has no findings; exit=0
```

## JSON report structure

The real application report is written to `reports/semgrep.json`. The report has
a top-level `results` list for findings, `errors` for scanner/analysis errors,
`paths.scanned` for scanned files, and `version` for the scanner version.

Local validation on 2026-10-21 with Semgrep 1.182.0 completed without analysis
errors. The insecure temporary example produced one finding and exit 1; the
parameterized replacement produced no findings and exit 0. The application scan
produced one finding, reported below, and exit 0 in reporting mode:

| Rule | File | Location | Severity |
| --- | --- | --- | --- |
| `python-sql-query-concatenation` | `app/app.py` | Line 94, columns 26-31 | `ERROR` (HIGH) |

The reported location is the query argument passed into `db.execute(query)`;
the concatenation that produces it is on line 91. This existing application
finding remains visible intentionally. Only the temporary validation example
was remediated. A hosted GitHub Actions run has not been verified locally.

Each finding provides:

| JSON field | Meaning |
| --- | --- |
| `results[].check_id` | Rule/check ID |
| `results[].path` | Source file |
| `results[].start.line`, `start.col` | Start location |
| `results[].end.line`, `end.col` | End location |
| `results[].extra.severity` | Rule-assigned severity |
| `results[].extra.message` | Finding description and remediation guidance |
| `results[].extra.metadata` | Optional CWE, technology, and confidence information |

Older severity names `ERROR`, `WARNING`, and `INFO` correspond to `HIGH`, `MEDIUM`,
and `LOW`. Current Semgrep also supports `CRITICAL`. The rule author assigns the
severity; severity does not itself control the command's exit status. In this
project the YAML uses `ERROR` and `WARNING`; inspect the report for emitted values.

To inspect the saved report in PowerShell:

```powershell
$report = Get-Content reports/semgrep.json -Raw | ConvertFrom-Json
$report.results | ForEach-Object {
    [PSCustomObject]@{
        Severity = $_.extra.severity
        Rule = $_.check_id
        File = $_.path
        Line = $_.start.line
        Description = $_.extra.message
    }
} | Format-Table -Wrap
```

## CI behavior and artifacts

`SAST (Semgrep)` runs alongside secret scanning on the workflow's existing push
trigger. Both must succeed before `Build and test` runs. This phase preserves
the existing trigger configuration.

The actual application scan is intentionally in reporting mode: `semgrep scan`
without `--error` records findings but does not fail simply because they exist.
This preserves visibility into the deliberately vulnerable training app.
`--strict` makes analysis warnings/errors fail the scan. Installation failures,
invalid rules, and validation failures also fail the job. Nothing uses
`continue-on-error` to conceal scanner failures. Add `--error` to the application
scan when the project is ready to block builds on findings.

The workflow always attempts to upload `reports/semgrep.json` as `semgrep-report`,
including after scan failure, retaining it for seven days. If an earlier step
fails before a report exists, inspect the failed step's logs. Download it from
Actions -> Security CI -> the relevant run -> Artifacts. Controlled validation
reports are temporary; the artifact contains only application findings.
